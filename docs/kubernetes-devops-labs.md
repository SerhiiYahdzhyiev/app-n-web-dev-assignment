# Практический план: Kubernetes и эксплуатация

Пошаговое прохождение с отдельными заданиями: [единый практикум](lab-sequence.md).

Дата: 2026-10-25. Статус: согласуемая исходная версия по результатам осмотра репозитория и ПК.

## Цель и формат

Использовать существующий e-commerce как стенд. Баланс общего маршрута — примерно 50/50 между эксплуатацией Kubernetes и проектированием приложения. Второй трек описан в [application-roadmap.md](application-roadmap.md).

Каждая лабораторная: воспроизводимый исходник → намеренная неисправность → диагностика → исправление → повторный эксперимент. Сохранять команды, конфигурацию, измерения и короткий разбор. Теоретические занятия в план не включены.

## 1. Имеющиеся ресурсы

Измерено на ПК через WSL и Windows CIM, без изменения системы:

| Ресурс | Результат |
| --- | --- |
| CPU | AMD Ryzen 5 3600, 6 ядер / 12 потоков |
| RAM хоста | 31,9 GiB |
| ОС хоста | Windows 11 Home |
| Текущая Linux-среда | WSL2, около 15 GiB доступной ей RAM; это не отдельная физическая машина |
| Свободно на томах Windows | C: ~376 GiB; D: ~406 GiB; E: ~530 GiB |
| Накопители | Windows сообщает SSD для четырёх обнаруженных физических дисков |
| Сеть | Intel AX200 Wi-Fi; Ethernet существует, но сейчас не подключён |

Объём виртуального диска WSL не следует считать свободным местом физического накопителя. Свободное место выше — снимок состояния, а не резерв для лаборатории.

Также доступны Lenovo Legion (характеристики и свободный диск ещё неизвестны) и Raspberry Pi 400 (у этой модели штатно 4 ГБ RAM; ОС и накопитель ещё нужно проверить).

Сеть общежития имеет изоляцию клиентов; доступна административная Wi-Fi-сеть без заявленной изоляции. Фактическую связность нужно проверить. Собственный роутер планируется позднее.

## 2. Рекомендуемая начальная топология

Начать с двух Linux-VM на разных физических машинах, K3s:

| VM | Хост | Назначение | Начальный бюджет |
| --- | --- | --- | --- |
| lab-server-1 | ПК | K3s server и workloads | 2 vCPU, 4 GiB RAM, 35–40 GiB диск |
| lab-worker-1 | Legion | K3s agent и лёгкие workloads | 2–4 vCPU, 4 GiB RAM, 25–35 GiB диск |
| lab-worker-2, позже | ПК | ML и дополнительная площадка scheduling | 4 vCPU, 6–8 GiB RAM, 50–60 GiB диск |

Ресурсы предварительные: ограничение Legion может потребовать перенести ML, сборки и мониторинг на ПК. Если ML не помещается в первый этап, добавить вторую VM на ПК раньше. На ПК оставить запас для Windows, IDE и WSL; их потребление суммируется с VM.

Диски thin-provisioned экономят первоначальное место, но могут вырасти до заданного размера. Образы PyTorch, build cache, snapshots VM и метрики требуют отдельного контроля. Образы собирать на ПК/CI, на Legion только скачивать runtime-образы. Не держать там registry и длинную историю метрик.

Windows Home не предоставляет поддерживаемую штатную роль Hyper-V для обычных VM. Практический вариант — актуальный VMware Workstation либо VirtualBox с поддержкой текущего Windows/WSL2. Проверить запуск одной VM и производительность до создания всего стенда; не отключать VBS/WSL наугад. Linux ставить непосредственно в VM гипервизора Windows, без вложенной виртуализации в WSL.

### Несколько VM: зачем и какие ограничения

- Позволяют раздельно перезапускать ноды, задавать ресурсы, тренировать scheduling, drain и обновления.
- Несколько VM на одном ПК остаются одним физическим доменом отказа.
- Два server и один server на другом хосте дают кворум etcd только пока жив хост с двумя участниками. Такая схема пригодна для тренировки отказа VM, но не переживает потерю любого из двух хостов.
- Дополнительные worker полезнее, чем раннее размножение control plane. Сначала один server и один-два worker.
- Добавить собственную метку физического хоста и topology spread/anti-affinity по ней. Разные kubernetes.io/hostname обозначают VM, а не независимое железо.
- Автостарт VM, сон Windows и действия при закрытии крышки ноутбука — часть стенда. Обновление Windows является отказом всех её VM одновременно.

## 3. Сеть сейчас: NAT + VPN внутри каждой VM

Рекомендованный старт: обычный NAT-адаптер каждой VM и Tailscale внутри Linux-гостей. VPN на Windows сама по себе не делает гостей взаимно доступными.

```text
VM на ПК ── NAT Windows ── Wi-Fi ── NAT Windows ── VM на Legion
    └──────────── частная VPN-сеть между гостями ────────────┘
```

Это L3-связность: общий Ethernet broadcast domain не требуется. При изоляции клиентов VPN может использовать relay; возможность установить соединение зависит от доступности сервиса и правил сети. Relay и Wi-Fi добавляют задержку, поэтому сначала измерить результат. Использовать только разрешённый доступ к сети.

До установки Kubernetes:

1. Проверить исходящий доступ, DNS и синхронизацию времени в гостях.
2. Проверить двустороннюю VPN-связность; выяснить direct/relay через диагностику Tailscale.
3. Измерить RTT, потери и пропускную способность между VM, включая передачу крупных пакетов.
4. Назначить уникальные hostname. Проверить отсутствие пересечений VPN, LAN, VM NAT, Pod CIDR и Service CIDR. Дефолты K3s: pods 10.42.0.0/16, services 10.43.0.0/16; не выбирать их без проверки существующих маршрутов.
5. Зафиксировать node IP из VPN и для обычного Flannel указать интерфейс VPN (`node-ip`, `flannel-iface`); для server настроить адрес API/advertise и TLS SAN под используемый endpoint. Параметры проверить по выбранной версии K3s и сохранить в конфигурации. Не включать параллельно второй VPN-backend K3s.
6. Разрешить внутри VPN необходимые порты: TCP 6443 к server, UDP 8472 между нодами для Flannel VXLAN, TCP 10250 для kubelet/metrics; при embedded etcd — TCP 2379–2380 между servers. Не публиковать их в интернет.
7. Проверить Pod→Pod между нодами и Service→Pod. Отдельно проверить MTU: VXLAN поверх VPN добавляет инкапсуляцию. Симптомы — маленькие запросы работают, крупные зависают.

В этой схеме NodePort на VPN-IP ноды удобен для первоначального входа в Traefik. Клиенту тоже нужна VPN-связность либо доступ через отдельный настроенный шлюз. Для локального имени приложения на первом этапе достаточно hosts-записи. После этого добавить DNS и TLS.

Метод L2 advertisement MetalLB не рассчитан на раздельные NAT-сети VM и обычную L3 VPN. Его оставить для собственной LAN. Ingress обеспечивает HTTP-маршрутизацию, но сам не создаёт внешнюю связность.

Bridge через Wi-Fi можно проверить как альтернативу: работоспособность зависит от гипервизора, драйвера и AP, включая ограничения дополнительных MAC/клиентов. Не строить весь план на предположении, что он обязательно заработает. Проброс одного TCP 6443 через NAT недостаточен для сети Kubernetes.

### После покупки роутера

- Выбрать модель с подходящим режимом подключения к существующему Wi-Fi uplink; наличие Wi-Fi у MikroTik не гарантирует нужную схему и скорость.
- Создать собственную LAN, DHCP reservations и локальный DNS. По возможности подключить ПК, Legion и Pi кабелями к своей LAN; upstream при этом может оставаться Wi-Fi.
- NAT на границе своей сети допустим: входящие соединения из интернета для лаборатории не обязательны.
- Сначала проверить связь VM через bridged Ethernet. Вложенные NAT-сети автоматически не исчезнут после покупки роутера.
- Предпочесть переустановку небольшого учебного кластера из автоматизации при смене адресации, а не ручную массовую замену node IP.
- Позднее проверить MetalLB L2, устойчивую точку входа и локальные сетевые отказы.

## 4. Лабораторные и критерии готовности

### K0. Воспроизводимый baseline

Запустить Compose из чистого состояния. Зафиксировать версии, seed и smoke-сценарий: регистрация → каталог → заказ → рекомендации. Создать k6-сценарий с фиксированными данными. Измерить ресурсы, отдельно старт ML и его steady state.

Готово: запуск повторяем, результат и исходные показатели сохранены. Изменения приложения: A0.

### K1. Собрать две ноды

Создать VM, настроить сеть по разделу 3, установить фиксированную версию K3s. Сначала вручную, затем описать подготовку Linux и установку в Ansible. Проверить kubeconfig, DNS, межнодовый pod traffic.

Готово: обе ноды Ready, VM можно пересоздать по инструкции. Выключение worker не лишает доступа к API.

### K2. Перенести приложение

Собственные plain YAML: Namespace, Deployment, Service, ConfigMap, Secret. MongoDB — один экземпляр и PVC, Redis — явно восстанавливаемый кэш. Для singleton с диском выбрать StatefulSet либо безопасную стратегию без двух одновременных writers. Embed пока один экземпляр. Traefik + Ingress; проверить сохранение семантики удаления `/api/` из текущего nginx.

Образы из registry, фиксированные теги/digest. Секреты не хранить plaintext в Git. Затем добавить Kustomize base/overlays. Учесть отсутствие гарантий порядка старта зависимостей.

Поломки: ImagePullBackOff, неверный selector, порт, конфигурация БД.

Готово: развёртывание воспроизводимо, диагностика опирается на events/logs/endpoints, а не случайные рестарты.

### K3. Жизненный цикл и отказ ноды

Внедрить A1: probes, shutdown, timeouts. По две реплики backend/recommend, requests/limits, topology spread, rolling update, PDB. Измерять долю ошибок и время восстановления.

Эксперименты: удалить pod, выполнить rollout/drain, выключить worker, остановить Redis/embed. Отличать voluntary disruption от аварии: PDB не спасает от отключения питания. Liveness не должна зависеть от здоровья удалённой БД. Для медленного ML — startup probe.

Готово: предсказуемые rollout и деградация; зафиксированы пределы доступности singleton БД и одного server.

### K4. Сеть и ограничения доступа

Проследить запрос от клиента до БД. Добавить TLS, NetworkPolicy default deny и явные разрешения, включая DNS. Проверить enforcement действующим сетевым стеком. Настроить минимальные ServiceAccount/RBAC, non-root и ограничения контейнеров там, где позволяют образы.

Поломки: запрет DNS, запрет Redis, неверный ingress route, MTU. Проверить, что разрешённые сценарии работают, запрещённые действительно блокируются.

Готово: источник ошибки локализуется до конкретного перехода; есть проверяемая матрица доступа.

### K5. Диски и восстановление

Начать с local-path storage. Выключить ноду с MongoDB и объяснить, почему её PVC не переезжает вместе с pod. Настроить backup CronJob и восстановление в отдельный namespace/volume. Копия должна переживать потерю исходного диска и быть доступна независимо от него.

Измерить RPO/RTO. Проверить восстановление кэша и пересоздание индекса. StatefulSet не обеспечивает репликацию БД, snapshot VM не заменяет согласованный backup приложения.

Готово: восстановление доказано проверкой данных. Distributed storage и DB replication — следующий отдельный эксперимент, когда хватает дисков и сети.

### K6. Наблюдаемость и ресурсы

Prometheus/Grafana с небольшим retention, JSON-логи stdout, correlation ID; затем OpenTelemetry tracing. Не ставить весь стек логов/трейсов одновременно на ограниченный Legion. Метрики: latency/errors, CPU throttling, RAM/OOM, saturation, cache hit rate, позднее queue lag.

Эксперименты: нагрузка, OOMKilled, ограничение CPU, медленная БД. HPA для stateless-компонента с настроенными requests и metrics. У HPA должны быть свободные ресурсы на нодах; автоматически добавить физическую машину он не может.

Готово: найдено узкое место и объяснено, когда увеличение replicas помогает, а когда усугубляет перегрузку зависимостей.

### K7. CI/CD и GitOps

CI: проверки → сборка → registry → обновление желаемой версии. Argo CD, overlays, immutable images. Секреты — например SOPS с выбранным механизмом расшифровки GitOps; ключ восстановления хранить отдельно. Проверить drift и неудачный rollout.

Готово: развёртывание идёт из Git, откат приложения проверен. Совместимость миграций данных проверяется отдельно; rollback образа не откатывает БД.

### K8. Распределённое приложение

Выполнить A2–A4 второго плана. Развернуть брокер, worker и собственную проекцию рекомендаций. Метрики lag, retries, DLQ. Проверить backlog после простоя ML и масштабирование consumers без порчи данных.

Готово: API сохраняет товар при недоступном ML, события догоняются, повторная доставка безопасна.

### K9. ARM, HA и восстановление кластера

Подключить Pi 400 как agent с 64-bit Linux. Сначала лёгкие workloads. Собирать multi-arch images только для проверенных зависимостей; ML и несовместимые образы ограничить amd64. Проверить nodeSelector/affinity и ошибку запуска неподходящей архитектуры.

HA — отдельная расширенная лабораторная: три server на трёх физических хостах, embedded etcd, стабильный API endpoint, backup datastore и восстановление. Pi использовать как server только после оценки SSD, сети и нагрузки; microSD не закладывать под etcd. Сначала допустимо изучить кворум на трёх VM двух хостов с явно ограниченной физической отказоустойчивостью.

Обновить K3s по нодам, заменить ноду, восстановить control plane. Backup etcd не содержит данные PVC приложений. Проверить отдельно отказ API endpoint, БД и ingress.

Готово: кластер и приложение восстанавливаются из автоматизации, секретов и проверенных backup; ограничения HA задокументированы.

## 5. Порядок совместной работы

K0/A0 → K1–K2 → A1/K3 → K4–K6 → K7 → A2–A4/K8 → A5 → K9. A6 (фронтенд) факультативен. Первые результаты получить до большой переработки бизнес-логики.

## 6. Что уточнить перед реализацией

- Legion: RAM, CPU, Windows edition, свободное место; возможность выделить 4 GiB и хотя бы 25–35 GiB диска.
- Pi: 64-bit ОС, накопитель, возможность SSD и тип сетевого подключения.
- Есть ли возможность законно подключить все устройства к выбранному Wi-Fi; как работает VPN direct/relay.
- Выбранный гипервизор и его совместная работа с текущим WSL2.
