# Roadmap приложения: подготовка к распределённому запуску

Пошаговое прохождение с отдельными заданиями: [единый практикум](lab-sequence.md).

Дата: 2026-10-25. Основа — статический осмотр текущего кода; работоспособность приложения пока не проверялась запуском.

Практика Kubernetes и топология стенда: [kubernetes-devops-labs.md](kubernetes-devops-labs.md). Цель этого трека — примерно половина общего обучения: проектирование, эксплуатационные контракты и поведение распределённой системы.

## Решение по проекту

Оставить текущий e-commerce. Уже есть API, рекомендации, ML, MongoDB, Redis и frontend. Начать с модульного core backend и постепенно выделить самостоятельную подсистему рекомендаций. Не дробить каждый CRUD-модуль только ради количества сервисов.

Микросервисная граница должна давать независимое владение данными, контракт и самостоятельный release lifecycle. Один репозиторий этому не мешает. Общая физическая СУБД на учебном стенде допустима, но доступ к чужим таблицам/коллекциям должен быть исключён отдельными ролями и контрактами.

## A0. Проверяемая исходная система

Задачи:
- Проверить сборки и запуск Compose; исправлять выявленные блокеры.
- Ввести детерминированный seed и smoke-тест основного сценария.
- Проверить существующие backend/__test__ и соответствие инструкций README реальному запуску тестов.
- Зафиксировать версии runtime/образов, lockfiles и воспроизводимую установку зависимостей.
- Измерить потребление ресурсов, загрузку модели, размер runtime-образов.

Результат: исходный сценарий повторяется, регрессии видны. Связь с инфраструктурой: K0.

## A1. Контракт приложения с Kubernetes

Задачи:
- Отдельные startup/readiness/liveness endpoints; исключить проверку внешних зависимостей из liveness.
- SIGTERM: перестать принимать новую работу, завершить активную в пределах бюджета, закрыть HTTP server/DB/broker connections. Проверить поведение через настоящий rollout.
- Конфигурация адресов, CORS и таймаутов через environment/config; одинаковые auth keys у реплик.
- Таймауты HTTP, проверка response status, ограниченные retries только для безопасных операций; не создавать retry storm.
- Fallback при недоступном embed и Redis. Если fallback требует БД, учитывать, что при падении БД он тоже недоступен.
- JSON-логи stdout, request/correlation ID, метрики latency/errors и зависимостей.
- Multi-stage runtime-образы, non-root где возможно. Подготовить модель для предсказуемого старта без обязательного скачивания из интернета при каждом pod restart.
- Проверить, что backend/recommend не требуют sticky sessions и не хранят необходимое состояние в локальном процессе.

Проверка: две реплики backend/recommend, rollout и остановка зависимостей под нагрузкой. Заранее определить допустимое поведение каждого endpoint.

Результат: stateless-сервисы масштабируются; ML пока singleton с явно известным ограничением. Связь: K2–K3.

## A2. Сделать состояние индекса явным

Сначала эксперимент: две реплики embed, запись нового товара, запросы к каждой реплике. Зафиксировать расхождение. Затем вернуться к одному writer до реализации новой схемы.

Минимальные исправления текущего FAISS:
- Устойчивое отображение product ID ↔ vector ID без усечения до 32 бит.
- Единый согласованный артефакт index + mapping + version либо детерминированный полный rebuild из первичных данных.
- Явная семантика upsert/delete, без накопления дубликатов при рестарте.
- Разделить rebuild и serving: не выдавать частично построенный индекс как готовый.
- Согласовать текст для индексации при initial build и изменениях товара.

Следующий архитектурный шаг: отделить вычисление embeddings от хранения и поиска. Выбрать один вариант после измерений:
- Qdrant — отдельный сервис векторного поиска.
- PostgreSQL + pgvector — меньше отдельных технологий, если PostgreSQL уже вводится для бизнес-данных.

В обоих случаях хранилище остаётся stateful и нуждается в backup; оно не становится HA от добавления Deployment replicas.

Результат: понятны источник истины, производный индекс и процедура восстановления. Связь: K5–K6.

## A3. Надёжная асинхронная индексация

Целевая цепочка:

```text
Core API → транзакция: товар + outbox
                         ↓
                    outbox relay → RabbitMQ → indexing worker → search storage
```

Задачи:
- События ProductCreated/ProductUpdated/ProductDeleted с event ID, product ID, entity version и schema version.
- Атомарная запись бизнес-изменения и outbox. Для многодокументных транзакций MongoDB нужен replica set; single-member replica set подходит для обучения транзакциям, но не обеспечивает HA. Альтернатива — перенос владельца этих данных в PostgreSQL.
- Relay отмечает публикацию после broker confirmation. Повторная публикация допустима и ожидаема.
- Consumer подтверждает событие после надёжной записи результата. Durable queue/message и publisher confirms настроены явно.
- Дедупликация/идемпотентный upsert, защита от устаревшей entity version, политика удаления.
- Ограниченные retries с backoff, DLQ, инструмент повторной обработки, метрики lag и возраста необработанных событий.
- Периодическая сверка/полный rebuild для исправления пропущенных или некорректных проекций.

Обязательные сценарии:
1. Broker недоступен, товар успешно сохранён вместе с outbox; после восстановления индекс догоняет.
2. Worker завершён после записи результата, но до acknowledgement; повторная доставка безопасна.
3. Событие доставлено дважды.
4. Более старое обновление приходит после нового.
5. Повреждённое событие уходит в DLQ, не блокируя очередь бесконечно.

Результат: at-least-once delivery с корректным бизнес-эффектом, без обещаний магического exactly-once. Связь: K8.

## A4. Самостоятельные рекомендации

Целевая схема:

```text
Frontend → Core API → core DB
              │
              ├→ outbox → broker → indexing worker → vector storage
              │                └→ recommendation projection
              └→ Recommendations API → projection / vector storage / cache
```

Задачи:
- Убрать прямое чтение core-коллекций из recommend. Для первого шага допустим ограниченный API владельца; целевая схема — собственная проекция событий каталога и доставленных заказов.
- Определить initial snapshot/backfill и обработку событий во время него, чтобы не потерять изменения.
- Исправить выбор персональных исходных товаров; определить fallback для нового пользователя и пустого каталога.
- Сохранить ранжирование поиска: выборка Product.find($in) сама по себе не гарантирует порядок входных ID.
- Версионировать cache keys/проекции; определить TTL и инвалидацию.
- Контракт API: таймаут, fallback, минимальный набор полей, допустимая давность рекомендаций.
- Контрактные тесты и отдельные релизы producer/consumer с совместимыми версиями событий.

Результат: рекомендации выкладываются и масштабируются независимо; временная неактуальность измеряется, а не скрывается.

## A5. Транзакционный сценарий заказов

После надёжной индексации добавить второй содержательный распределённый сценарий.

Первый milestone — модель данных:
- PostgreSQL для orders/order_items и inventory/reservations, если выбран этот путь.
- Snapshot цены, названия и количества в заказе; валюта и определённое представление денег.
- Idempotency key создания заказа с ограничением уникальности в БД.
- Явные переходы статусов, конкурентное резервирование остатков, освобождение резерва.
- Миграции expand/contract и проверка совместного запуска старой и новой версии.

Второй milestone — границы сервисов:
- Сначала реализовать транзакционные инварианты в модульном backend.
- Затем выделить Orders/Inventory по реальной ответственности и определить владельцев данных.
- Добавить mock payment provider: задержка, отказ, повторный callback.
- Описать компенсации и eventual consistency вместо распределённой транзакции между сервисами.

Эксперименты: два покупателя на последнюю единицу, повтор запроса после timeout, повторный callback, падение процесса после оплаты, истечение резерва.

Результат: нет двойного заказа/списания от повторов, нет необъяснимого отрицательного остатка, незавершённые процессы обнаруживаются и восстанавливаются.

Миграция MongoDB → PostgreSQL должна включать mapping ID, backfill, сверку данных, момент переключения и план возврата. Не вводить ненадёжную двойную запись в две БД как постоянное решение.

## A6. Факультативный frontend

Замена Angular на предпочитаемый фреймворк — отдельный milestone после основного маршрута. Для основной цели полезнее сначала:
- Обработка временной недоступности рекомендаций без поломки каталога/checkout.
- Понятное отображение pending-состояний асинхронных операций.
- Совместимость frontend с двумя соседними версиями backend.
- E2E ключевого пользовательского сценария.

## Итоговые артефакты

- Краткие ADR: границы сервисов, владелец данных, выбор search storage/broker, гарантии доставки.
- Контракты HTTP и событий, включая ошибки, версии и идемпотентность.
- Нагрузочные сценарии и результаты до/после рефакторинга.
- Runbooks: rebuild индекса, replay DLQ, восстановление проекций, зависшая обработка заказа.
- Практические интеграционные тесты на сбои и конкурентность; не ограничиваться unit-тестами, повторяющими реализацию.

Первый полезный рубеж: исходный магазин работает на двух физических хостах, backend обновляется под нагрузкой, отказ рекомендаций не ломает основной пользовательский путь. Второй: индексация и рекомендации стали действительно независимой подсистемой.
