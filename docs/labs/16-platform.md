# 16. Эксплуатация платформы и финальные учения

[Маршрут](../lab-sequence.md) · Нужно: 01–15

## Цель
Воспроизвести и восстановить стенд целиком, различая отказ приложения, VM и физического хоста.

## Обязательная часть
1. Собери подготовку Linux/сети/K3s в автоматизацию, например Ansible. Пересоздай worker, не копируя вручную состояние старой VM.
2. Добавь Pi 400 с 64-bit Linux как worker. Проверь multi-arch image для лёгкого сервиса, а неподдерживаемые зависимости ограничь amd64. Если Pi ещё не подготовлен, зафиксируй этот блок как ожидающий железа.
3. Обнови K3s по нодам в пределах поддерживаемого пути версий. Используй baseline-трафик, dashboard и alerts.
4. Проверь backup/restore datastore control plane отдельно от данных приложений. Для текущего SQLite и будущего etcd процедуры отличаются; нужны соответствующие конфигурация и ключевой материал.
5. Выполни game day: выбери один заранее ограниченный отказ, предскажи эффект, восстанови систему по runbook, составь краткий postmortem.

## Расширение при подходящем железе: HA
Три server с embedded etcd, стабильный API endpoint и три физических домена отказа. Если используются три VM на двух хостах, отдельно покажи асимметрию потери кворума при размещении 2+1. Pi как server допустим только после оценки SSD, сети и доступных ресурсов.

Проверь отказ одного server, API endpoint, ноды с БД и ingress отдельно. HA control plane не означает HA всех компонентов. Один домашний роутер и питание могут остаться общими точками отказа — это ограничение стенда, которое нужно описать.

## Проверка мониторинга
Останови внутренний сборщик метрик и проверь независимое обнаружение потери мониторинга. Выключи один физический хост: какие VM исчезли, откуда приходит уведомление, доступна ли история? У внешнего наблюдателя должны быть понятны собственные зависимости и границы отказа.

## Финальная приёмка
- Есть воспроизводимая сборка стенда, inventory и зафиксированные версии.
- Восстановлены control plane и пользовательские данные; проверен smoke и небольшой baseline.
- Собраны реальные RPO/RTO, ошибки и время восстановления хотя бы для отказа pod, worker и зависимости.
- Есть схема физических/виртуальных доменов отказа, список оставшихся SPOF и ресурсный бюджет.
- Все изменения платформы и приложения наблюдаемы; итоговые выводы подтверждены артефактами, а не только скриншотом Running pods.

## Подсказки
K3s upgrade/backup documentation, version skew policy, etcd quorum, backup encryption keys, failure domains, external heartbeat. Восстановление в новом окружении сильнее доказывает воспроизводимость, чем удачный reboot старого.

Рубежи: автоматизация → ARM → upgrade → restore → game day → необязательный HA.
