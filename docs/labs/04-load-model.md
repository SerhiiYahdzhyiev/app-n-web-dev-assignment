# 04. Реалистичная модель нагрузки

[Маршрут](../lab-sequence.md) · Нужно: 01, 03 · Далее: [05](05-first-deploy.md)

## Цель
Создать генератор пользовательских путешествий, пригодный для сравнения версий и экспериментов с отказами.

## Выбор инструмента
Выбери один основной инструмент и кратко объясни выбор. **Locust** удобен для stateful Python-сценариев, cookies, последовательностей и моделирования поведения пользователей. **k6** удобен для JS-сценариев и заданной интенсивности поступления запросов через arrival-rate executors. Не требуется поддерживать оба.

## Задание
1. Описать пользователей как последовательности действий, а не независимые случайные запросы.
2. Создать повторяемый набор синтетических пользователей/товаров/заказов. Параметризовать seed, target, duration, concurrency/rate и профиль.
3. Реализовать think time, сессии и разные данные. Проверять бизнес-результат ответа; ошибочный заказ с HTTP 200 должен считаться ошибкой.
4. Отделить подготовку/очистку данных от измеряемого интервала. Для повторов использовать run ID или отдельный набор данных.
5. Собирать offered/achieved throughput, active users, p50/p95/p99, ошибки по операциям, CPU/RAM/сеть генератора. Для arrival-rate режима учитывать непущенные/пропущенные итерации.

## Стартовая гипотеза поведения
Это синтетическая гипотеза, а не реальные продуктовые данные. Начни с долей **сессий**, затем измерь фактическую смесь запросов:

| Сессия | Доля | Поведение |
| --- | --- | --- |
| Посетитель | 60% | Каталог → 2–5 карточек → поиск → уход |
| Возвращающийся клиент | 25% | Вход → рекомендации → карточки → история заказов |
| Покупатель | 15% | Вход → каталог/карточки → оформление заказа → проверка результата |

Используй доступные API: корзина может быть локальным состоянием SPA, а не серверным endpoint. Admin-изменения запускай отдельным редким потоком. Добавь новых пользователей без истории. Популярные товары должны запрашиваться чаще остальных: сравни skewed/hot-set и равномерное распределения. Think time варьируй, например в пределах нескольких секунд, а не фиксированным нулём.

## Обязательные профили
- **Smoke:** несколько пользователей, проверка корректности.
- **Baseline:** разминка, затем стабильная небольшая нагрузка с фиксированной конфигурацией.
- **Ramp/stress:** ступени интенсивности до заранее установленного предела latency/errors/ресурсов; затем остановка и восстановление.
- **Spike:** короткий ограниченный скачок и возврат к норме.
- **Soak:** сначала 30–60 минут; более длительный прогон позднее, если есть задача проверить утечку/рост данных.
- **Cold/warm:** сравнение холодного и прогретого кэша на контролируемом наборе данных.

Не смешивай холодный старт модели и steady-state benchmark. Для короткого прогона с малым числом запросов p99 может быть нестабилен: сохраняй sample count и повторяй сравнение при необходимости.

## Важное различие моделей
Locust с фиксированным числом пользователей обычно задаёт **closed workload**: при замедлении сервера падает частота новых действий. Это реалистично для ограниченной группы пользователей, но может скрыть перегрузку. Для независимого притока новых запросов нужен **open workload**: arrival-rate режим подходящего инструмента или обоснованная реализация. Load shape с ростом числа пользователей не эквивалентен гарантированной arrival rate.

## Эксперименты и приёмка
- Сравни одинаковое число пользователей с разным think time: объясни различие RPS.
- Отключи embed и проверь, что отчёт различает fallback и ошибку.
- Убедись, что генератор сам не упирается в CPU, сеть или connection pool.
- Сохрани сценарии, dataset/config, версии, отчёт baseline и stop conditions.

По возможности размещай генератор вне измеряемых нод. Если он на том же ПК, фиксируй совместное потребление и не выдавай результат за независимый capacity benchmark. Для нагрузочного сравнения сначала используй стабильно доступную точку входа, позже отдельно сравни внешний ingress и внутренний Service.

## Подсказки
Locust User/HttpUser/TaskSet, wait_time, custom load shape; k6 scenarios/arrival-rate; coordinated omission, Little's Law, connection reuse. HTTP-генератор не выполняет Angular и не измеряет browser rendering: для UI используй отдельный малочисленный browser smoke, например Playwright.

Рубежи: одна сессия → три класса поведения → baseline → остальные профили.
