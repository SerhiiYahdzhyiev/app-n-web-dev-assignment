# 07. Жизненный цикл и отказоустойчивость

[Маршрут](../lab-sequence.md) · Нужно: 04–06 · Далее: [08](08-network-tracing.md)

## Цель
Добиться предсказуемых обновлений и деградации под пользовательской нагрузкой.

## Задание
1. Реализуй отдельные startup/readiness/liveness checks и graceful shutdown для сервисов.
2. Введи deadlines/timeouts и явное поведение при отказах Redis/embed. Определи, какие retries безопасны.
3. Запусти две реплики backend/recommend, настрой requests/limits, rollout, PDB и распределение по физическим хостам.
4. Определи бюджет завершения запросов и связь с termination grace period. Учти соединения, которые уже были открыты при начале остановки.

## Эксперименты
Под стабильной нагрузкой отдельно: удалить pod; выпустить новую версию; выполнить drain worker; резко выключить worker; отключить Redis; отключить embed. Перед каждым записать прогноз, после — errors, p95/p99 и recovery time.

Не выключай единственный server в первом тесте worker failure. Для singleton БД предскажи влияние её размещения заранее.

## Приёмка и артефакты
- Readiness не выпускает неподготовленный pod в трафик; startup допускает медленную загрузку модели.
- Отказ зависимости не запускает бесконечную волну liveness-рестартов.
- Rollout и восстановление измерены; причины оставшихся ошибок объяснены.
- Рекомендации деградируют по определённому контракту, основной сценарий сохраняет работоспособность там, где это архитектурно возможно.

## Подсказки
SIGTERM, endpoint propagation, keep-alive, graceful server close, topologySpreadConstraints, custom physical-host label. PDB регулирует добровольные disruptions, а не физический отказ. Разные VM hostname не означают разные физические хосты.

Рубежи: lifecycle приложения → replicas → rollout → отказы.
