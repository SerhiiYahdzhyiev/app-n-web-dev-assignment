# 03. Минимальная наблюдаемость приложения

[Маршрут](../lab-sequence.md) · Нужно: 01 · Далее: [04](04-load-model.md)

## Цель
Уметь наблюдать приложение до нагрузочных и кластерных экспериментов.

## Задание
1. Добавь структурированные stdout-логи: service, version, request ID, route, duration, result. Передавай request ID между HTTP-компонентами.
2. Инструментируй backend/recommend/embed: количество запросов, ошибки, распределение длительности, активные запросы, длительность обращений к зависимостям.
3. Добавь показатели кэша и ML: hit/miss, время вычисления embedding, время построения индекса, его размер/готовность.
4. Определи пользовательские SLI: успешное чтение каталога, корректное создание заказа, успешные/деградированные рекомендации. Выбери предварительные учебные цели, не называя их production SLA.
5. Сделай метрики доступными локальному сборщику или просмотру; большой мониторинговый стек пока необязателен.

## Эксперимент
Выполни успешный запрос, некорректный запрос и запрос при отключённом embed. По логам и метрикам объясни каждый результат. Отличай ожидаемые 4xx от ошибок сервера и degraded response от полноценного успеха.

## Приёмка и артефакты
- Один запрос прослеживается через участвующие сервисы.
- Histogram buckets позволяют оценить выбранные latency-цели.
- Labels ограничены: нет user ID, product ID, raw URL или request ID в метриках. Секреты и пароли не попадают в логи.
- Сохранены словарь метрик и определения SLI, включая числитель и знаменатель.

## Подсказки
RED metrics, Prometheus client libraries, histogram vs summary, metric cardinality, route templates. Логи и метрики дополняют друг друга; средняя latency скрывает медленные хвосты.

Рубежи: логи → HTTP-метрики → зависимости → проверка трёх исходов.
