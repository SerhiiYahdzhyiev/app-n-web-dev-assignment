# 14. Самостоятельный сервис рекомендаций

[Маршрут](../lab-sequence.md) · Нужно: 12–13 · Далее: [15](15-orders.md)

## Цель
Убрать зависимость рекомендаций от чужой схемы БД и получить независимый release lifecycle.

## Задание
1. Спроектируй собственную проекцию каталога и истории доставленных заказов. Определи владельца каждой сущности.
2. Реализуй bootstrap/backfill с последующим применением событий без потери изменений на границе этих процессов.
3. Убери прямой доступ recommend к core-коллекциям и проверь это отдельными credentials/permissions.
4. Исправь персонализацию: текущая агрегация top product глобальная. Сохрани порядок ранжирования при загрузке найденных товаров.
5. Определи API, допустимую давность данных, fallback, TTL/инвалидацию кэша и правила совместимости событий.

## Эксперименты
- Изменение товара/заказа во время bootstrap.
- Временная остановка consumer и последующее догоняние.
- Поочерёдный rollout producer/consumer с соседними версиями контракта.
- Нагрузка новыми и возвращающимися пользователями; сравнение warm/cold cache и поведения без персональной истории.

## Приёмка и артефакты
Сервис читает только собственное состояние и оговорённые API. Есть контрактные проверки, backfill runbook и графики freshness/fallback/cache hit rate. Контрольные пользователи получают объяснимые результаты; отсутствующие/удалённые товары не ломают ответ. Релиз рекомендаций не требует одновременного релиза core.

## Подсказки
Database per service (логическое владение не требует отдельного физического сервера), materialized projection, schema evolution, bootstrap watermark. HTTP latency и качество рекомендаций — разные показатели; быстрого ответа недостаточно для проверки корректности.

Рубежи: контракт → проекция → запрет общей БД → независимый rollout.
