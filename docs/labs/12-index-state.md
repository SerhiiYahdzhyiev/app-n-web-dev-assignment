# 12. Состояние и жизненный цикл индекса

[Маршрут](../lab-sequence.md) · Нужно: 09, 11 · Далее: [13](13-events.md)

## Цель
Разобраться, почему текущий embed нельзя просто масштабировать, и исправить жизненный цикл индекса.

## Задание
1. Запусти две тестовые реплики embed. Добавь товар и обратись к каждой реплике отдельно. Зафиксируй различие состояния, затем верни singleton до исправления.
2. Проверь повторный startup с сохранённым FAISS, соответствие id_map, update/delete и коллизии усечённых ID.
3. Определи единый формат текста для embedding, устойчивые ID и семантику upsert/delete.
4. Реализуй согласованный index+mapping+version либо детерминированный rebuild. Не отдавай частично построенный индекс как готовый.
5. Прими ADR: оставить исправленный FAISS на этом этапе или отделить вычисление embeddings от поиска через Qdrant/pgvector. Выбери один следующий путь, не внедряй оба.

## Эксперименты
Повторный rebuild; рестарт посередине построения; создание/изменение/удаление товара; запрос во время переключения версии индекса.

## Приёмка и артефакты
Нет накопления дубликатов, неизвестных ID и необъяснимого исчезновения товаров. Rebuild повторяем, результат проверяется по набору контрольных товаров. Мониторинг показывает готовность, версию, размер индекса и длительность rebuild. Ограничения конкурентной записи описаны.

## Подсказки
Derived state, atomic snapshot publication, idempotent upsert, index versioning. Векторное хранилище тоже нуждается в backup/restore или доказанном rebuild; увеличение replicas не решает согласованность автоматически.

Рубежи: воспроизведение → модель состояния → исправление → rebuild-тест.
