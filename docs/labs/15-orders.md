# 15. Транзакционные заказы и конкурентная нагрузка

[Маршрут](../lab-sequence.md) · Нужно: 11, 13–14 · Далее: [16](16-platform.md)

## Цель
Проверить бизнес-инварианты, которые Kubernetes не может обеспечить вместо приложения.

## Задание
1. Определи инварианты заказа, оплаты и остатков, прежде чем менять схему.
2. Реализуй order item snapshots, количество, валюту и определённое представление денег; idempotency key с ограничением уникальности.
3. Введи PostgreSQL для выбранного транзакционного модуля. Подготовь mapping ID, migration/backfill, сверку и переключение без ненадёжной постоянной двойной записи.
4. Реализуй конкурентное резервирование, срок резерва и явные переходы статусов сначала внутри модульного backend.
5. Добавь mock payment provider с задержками, отказами и повторными callbacks. Затем выдели Orders/Inventory по ответственности и опиши компенсации без общей распределённой транзакции.
6. Проверь expand/contract миграцию при одновременной работе двух соседних версий приложения.

## Реалистичная нагрузка
Расширь покупательскую сессию из 04. Добавь hot SKU с малым остатком, повтор после timeout с тем же idempotency key, повторный callback, отмену и истечение резерва. Проверяй не только response codes, но и итоговые balances/statuses. Большинство сессий по-прежнему читают каталог; выделенный конкурентный тест последней единицы запускается отдельно.

## Отказы
Падение после внешней оплаты до локального завершения; callback после отмены/timeout; два покупателя на последнюю единицу; повтор одного запроса; недоступность одного сервиса при завершении workflow.

## Приёмка и артефакты
Нет двойного заказа/списания от повторов и необъяснимого отрицательного остатка. Неоконченные процессы обнаруживаются и имеют путь восстановления. Мониторинг показывает reservation age, pending payment age, compensation failures и нарушения инвариантов. Есть state diagram, reconciliation job/runbook и отчёт конкурентных тестов.

## Подсказки
Unique constraints, transaction isolation, optimistic/pessimistic concurrency, saga compensation, reconciliation, expand/contract. Idempotency key должен иметь владельца, область действия и политику хранения. Ответ timeout не доказывает, что операция не состоялась.

Рубежи: инварианты → схема/миграция → резервы → mock payment → сервисные границы → отказы.
