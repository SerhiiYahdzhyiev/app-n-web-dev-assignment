# Практикум: последовательность заданий

Этот документ — точка входа в практикум. Архитектурный контекст: [план инфраструктуры](kubernetes-devops-labs.md) и [roadmap приложения](application-roadmap.md). Здесь они объединены в последовательность небольших проверяемых работ. Теорию и конкретные команды нужно найти самостоятельно.

## Как проходить

- Выполняй задания по порядку. Лабораторную можно разбивать на несколько вечеров: в каждой есть промежуточные рубежи.
- Для каждого задания заведи `docs/lab-results/NN/`: короткий отчёт, версии, конфигурация запуска, измерения, ссылки на коммиты и оставшиеся вопросы. Не сохраняй секреты и персональные данные.
- Перед экспериментом запиши ожидаемый результат и условие остановки. После — наблюдение и объяснение различий.
- После каждого задания оставляй воспроизводимую рабочую точку: код, manifests, scripts, seed. Ручные изменения фиксируй или переноси в автоматизацию.
- Задание завершено по критериям приёмки, а не по количеству установленных инструментов. Дополнительные эксперименты необязательны.
- Не публикуй генераторы нагрузки и административные интерфейсы наружу. Генерируй трафик только на собственный стенд, ограничивая его бюджетом ресурсов.

## Контрольные точки

1. **После 04:** система запускается, измеряется и получает воспроизводимую нагрузку.
2. **После 06:** магазин работает на двух хостах; видны здоровье платформы и пользовательский результат.
3. **После 11:** можно объяснить отказ, восстановить данные и безопасно доставить новую версию.
4. **После 14:** рекомендации стали независимой асинхронной подсистемой.
5. **После 16:** стенд восстанавливается из артефактов, а ограничения подтверждены экспериментами.

## Сквозная стратегия наблюдаемости

- **03:** метрики и логи приложения, без обязательного большого стека.
- **04:** качество и воспроизводимость нагрузки, метрики генератора.
- **06:** Prometheus/Grafana, инфраструктура и приложение, external availability probe, alerts.
- **08:** distributed tracing и связь trace ↔ log ↔ metric.
- **09:** backup age, restore duration, диски и состояние данных.
- **10:** saturation, capacity, autoscaling и контроль ложных выводов.
- **13–15:** lag, retries, DLQ, freshness, бизнес-инварианты.
- **16:** мониторинг самой системы мониторинга и сценарии полной потери площадки.

Графики нужны для ответа на вопрос, а не для количества панелей. Сохраняй dashboard/alert definitions в Git. Выбери короткий retention и ограниченные ресурсы; расширяй стек по мере необходимости. Отсутствие метрик нельзя автоматически интерпретировать как здоровье.
